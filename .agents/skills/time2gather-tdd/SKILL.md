# Time2Gather TDD

Time2Gather에서 기능이나 동작을 바꾸면 Red, Green, Refactor 순서로 개발한다. 시작할 때 해당 저장소의 AGENTS.md를 읽는다. 사용자 승인 범위와 현재 작업 트리의 다른 변경을 보존한다.

## 개발 순서

1. 바꿀 동작과 변경 전후의 기대 결과를 구체적으로 정한다. 버그는 실제 발생 조건을 먼저 고정한다.
2. 제품 코드를 바꾸기 전에 해당 동작의 테스트를 작성하고 실행한다. 기대 동작의 단언이 실패하는 것을 확인한다. 컴파일 오류, Docker 미실행과 설정 오류는 버그를 재현한 Red가 아니다.
3. 실패 원인을 해결하는 최소 구현을 추가한다. 동일 테스트가 통과하는 것을 확인한 뒤 관련 회귀 테스트를 실행한다.
4. 통과 상태를 유지하며 구조를 정리한다. 확인한 실패와 통과 명령, 테스트 수, 미검증 범위를 남긴다.

순수 리팩터링은 기존 동작을 지키는 테스트를 먼저 확인하고, 빠진 동작은 특성 테스트로 고정한다. 실패를 만들기 위해 정상 코드를 일부러 망가뜨리지 않는다. 문서나 단순 시각 변경에는 의미 없는 단위 테스트를 추가하지 않고 해당 산출물 검증을 수행한다.

## 서비스와 DB 검증

이 항목은 백엔드 저장 동작을 추가하거나 변경할 때 적용한다. 프런트엔드 동작은 해당 저장소의 package.json과 기존 단위 및 브라우저 테스트를 기준으로 실패 조건을 고정한다.

- 운영 저장소는 Firestore다. MySQL/JPA 테스트만 통과했다고 운영 DB 통합 검증을 완료했다고 보고하지 않는다.
- 서비스 또는 실제 API에서 Firestore SDK와 저장소까지 연결하는 테스트는 Testcontainers의 공식 Firestore 에뮬레이터를 사용한다. 에뮬레이터는 관리형 운영 서버 자체가 아니며 인덱스, 한도와 실제 경합 특성을 모두 보장하지 않는다.
- JPA 경로를 검증할 때는 MySQL Testcontainers를 사용한다. H2로 운영 DB의 동작을 대신 검증하지 않는다.
- 통합 테스트에서 서비스나 저장소를 Mockito로 대체하지 않는다. 명시적인 실패 주입이 필요한 경우 정상 I/O는 실제 DB로 수행하고, 무엇을 주입했는지 설명한다.
- 거절된 요청과 쓰기 실패 후 기존 데이터가 유지되는지 DB에서 다시 읽어 확인한다. 성공 응답이나 예외 종류만 검사하지 않는다.
- 응답 유실로 커밋 결과를 모르는 경우는 롤백이 확정된 실패와 구분한다. 멱등성 재시도나 재조회로 결과를 확인하는 동작을 검증한다.
- Firestore에서 Spring의 `@Transactional` 선언만으로 여러 SDK 쓰기가 롤백된다고 가정하지 않는다. 하나의 논리 변경은 실제 batch 또는 transaction 경계 안에서 검증한다.
- 투표 교체는 잘못된 ID, 다른 모임의 ID, 삭제된 후보를 가진 오래된 화면, 중복 요청, 동시 수정과 부분 저장 실패를 우선 검증한다. 개인 조회와 결과 집계의 일치도 확인한다.
- 테스트는 `demo-` 프로젝트와 폐기 가능한 DB만 사용한다. 일반 테스트가 운영 자격증명이나 운영 데이터에 의존하지 않게 한다.

## 실행과 완료 판단

백엔드 저장소의 기본 명령은 다음과 같다. 실제 task 정의가 바뀌었다면 현재 build.gradle을 기준으로 조정한다.

- `./gradlew test`: 빠른 단위 테스트와 컨트롤러 단위 검사
- `./gradlew firestoreTest`: 운영 저장소 기반 서비스와 DB 통합 검사
- `./gradlew mysqlTest`: JPA와 MySQL 통합 검사
- `./gradlew check`: 위 검사와 JaCoCo 보고서 및 커버리지 기준 검사

통합 검사에서 Docker가 없거나 테스트가 건너뛰어지면 완료로 처리하지 않는다. 실패를 숨기기 위해 환경 조건으로 테스트를 제외하거나 통과할 때까지 반복 실행하지 않는다. 일시 실패를 재검증했다면 첫 실패와 재실행 결과를 함께 남긴다.

JaCoCo 라인과 분기 수치를 함께 확인하고 서비스, 저장 계층 및 변경 클래스의 미검증 경로를 검토한다. 기준을 통과시키려고 클래스를 제외하거나 단언 없는 호출 테스트를 추가하지 않는다. 미배포 변경이 섞인 작업 소스의 수치를 운영 배포 소스의 수치로 보고하지 않는다.

테스트 통과는 요청 범위의 구현과 검증 완료를 뜻한다. 푸시나 운영 배포 권한을 새로 부여하지 않는다. 배포가 승인된 작업에서는 프로젝트의 기존 배포 지침과 후보 검증을 따른다.
